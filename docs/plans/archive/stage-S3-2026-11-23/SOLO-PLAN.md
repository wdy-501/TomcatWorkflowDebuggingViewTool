> 版本：v1.0（2026-11-20）  
> 状态：方案阶段；单人开发模式；尚未创建业务代码。  
> 产品主计划：[00-master-plan.md](00-master-plan.md)  
> 历史三人计划：[archive/](archive/)（已废弃，仅参考）

## 0. 单人模式的原则

- **一个人、一个工作区、一个活跃 Qoder 会话。** 不再使用 A/B/C 三个 owner、三个 worktree、三个并行分支；不再需要三人会签。
- **纵向切片优先。** 不先把整个 agent 写完再做 UI；每个检查点都尽量从“点击→请求→后端事实→工作台”打通一条最薄的链路。
- **检查点驱动，不按时间。** 完成一个检查点就停止、跑测试、写进度包、自检、提交；不按“第几天/第几周”决定是否继续。
- **先本地，后云端。** 本地 Boot + Vue 的 0 行/纯前端/回放先做扎实；React、Tomcat、L2、云端按检查点逐步加，不同时开工。
- **Qoder 是结对程序员，不是自动驾驶。** 每次只让它做一个检查点；高风险改动先 plan，写完跑测试，再让 review 会话/子代理自查。
- **遇到 GitHub/国内无镜像资源：给用户官方链接、版本、放置位置，由用户下载；不自动换第三方镜像。**
- **不把“看起来完整”当完成。** 未采集、截断、脱敏、云端未验证都必须明确写出来，并在支持矩阵里如实标注。

## 1. 单人范围分级（先保 MVP，不要一口气做三栈+云端）

| 级别 | 内容 | 目标 | 建议 |
|---|---|---|---|
| **MVP（建议先做）** | 本地 Spring Boot 2.7 + Vue3/Vite + Axios，0 行案例、纯前端案例、回放、工作台、L1、sourcemap、IDEA/JAR 接入 | 证明“首次失败即出图 + 0 行事实 + 纯前端没发请求 + 回放不重发” | 先做到 S5；这是最小可演示闭环 |
| **单人 V1** | 在 MVP 上增加 L2 行级变量、×3、异步、字段 diff、Vite/Vue 构建插件、可访问性/性能 | 能处理用户自己的真实项目 | S6–S7 |
| **扩展** | Tomcat WAR/SSM、React/Webpack、云端 Boot、云端 WAR | 覆盖三类环境和两种交付 | S7–S10；按截止日期裁剪 |
| **明确不先做** | WebFlux、微服务全链路、GraalVM native、像素级页面回放、云端外部数据库 | 容易把单人拖垮 | 放到以后或不做 |

**重要现实：** 三个人 21–30 周的估算不能直接平移到一个人。单人做完整三栈 + 云端的时间会显著更长；如果目标是比赛/课程演示，**优先锁定 MVP，不要同时承诺云端 WAR/React/Tomcat 全矩阵**。

## 2. 单人编程模式（Qoder）

### 2.1 工作区与分支

- 一个 Qoder workspace，指向单人工作目录；不再建 `A/B/C` 三个 worktree。
- 分支：
  - 推荐 `main` + 短分支 `feat/Sx-<name>`；每个检查点完成后合并/提交并打 tag。
  - 单人可以在 `main` 上小步提交，但每个检查点至少一个可回滚 commit。
- 不给每个“角色”开一个并行会话；同一时间只有一个 owner 会话在改代码。
- 需要审查时：用一个只读 review 会话/子代理，不另开一个会同时写同一模块的 owner 会话。

### 2.2 每个检查点的 Qoder 会话流程

1. 新会话或压缩上下文；加载：`README.md`、本文件、主计划的对应章节、当前契约/fixture。
2. 明确本次只做 `Sx`，写出验收命令和禁止修改范围。
3. 先让 Qoder 给计划（高风险用 plan 模式），再写代码。
4. 写测试/fixture，跑 demo；不要用“AI 说完成”当验收。
5. 到达检查点：**停止继续修改**，输出进度包（见第 4 节），做一次自检/review。
6. 自检通过后提交/tag，更新本文件；再开下一个检查点。
7. 不在一个会话里连续跨多个检查点；不按天/周决定继续，只看检查点是否完成。

### 2.3 Qoder 会话开场模板

```text
你是 TraceBoard 的单人开发结对助手。当前只做检查点 Sx。
先读 docs/plans/README.md、docs/plans/SOLO-PLAN.md、主计划对应章节、当前契约/fixture。
写入范围：本检查点相关文件；不要改其他模块/契约。
要求：先给计划/测试，再改代码；每次改动跑验收；不自动下载 GitHub/无镜像资源。
到达 Sx 检查点后停止继续修改，输出进度包并等待我确认，不要自动跨到 Sx+1。
```

## 3. 单人检查点（S0–S10）

每个检查点完成就停止一次，做自检；不按时间同步。

| ID | 检查点 | 主要工作 | 验收/完成信号 | 建议范围 |
|---|---|---|---|---|
| S0 | 基础与契约 | `git init`、目录/构建骨架、schema v1 草案、demo 应用骨架、0 行 fixture；不写复杂功能 | 仓库可构建；schema/传输/API 草案可评审；fixture 可读 | MVP |
| S1 | Walking skeleton | agent 最小插桩 + 一条事件；collector mock/ingest；工作台 fixture 板；点击/请求假事件 | 一条假事件从“点击/请求”到工作台；main 可运行 | MVP |
| S2 | 0 行事实链 | agent Controller/Service/Mapper/JDBC 行数；collector 关联/存储/API；工作台请求切换 | 首次失败点击可看到 SQL 0 行、Mapper 0、Service true、无异常 | MVP |
| S3 | 前端事实与回放 | runtime SDK 点击/控件/请求/DOM；纯前端空状态；状态语义；时间轴/只读回放 | 纯前端案例能证明“请求没发”；0 行案例可回放，回放 0 写 | MVP |
| S4 | 本地接入与详情 | 本地启动器 IDEA/JAR、预览代理/SDK 注入、诊断；节点详情、×N、SQL/UI 票签、缺口 | 新手按文档接入；案例 A/B 能走到结论；未采集有原因 | MVP |
| S5 | L1 与前端浅层 | L1 参数/实体字段、脱敏/截断；sourcemap；Vite/Vue 浅层插件；性能基线 | 100→0 在参数/字段层可见；前端行号/方法名可见（有 map/插件） | MVP 收尾 |
| S6 | L2 与异步 | 选中方法行级局部变量、字段写入、异步上下文、×3、预算/循环折叠 | 行级 100→0；×3 能指哪次坏；缺调试信息不猜 | V1 |
| S7 | 第二栈 | 任选 Tomcat WAR/SSM 或 React/Webpack 先做一条；不要两条一起 | 第二栈案例 A/B；本地可跑；支持矩阵如实标 | 扩展 |
| S8 | 第三栈/矩阵 | 另一条栈；本地矩阵；性能/兼容报告 | 三类环境本地可用；矩阵有证据 | 扩展 |
| S9 | 云端 Boot | 上传 Boot JAR、沙箱/强隔离、DB seed、预览、保留/清理、启动诊断 | 云端 Boot 案例 A/B；隔离/保留通过 | 云端（可选/后置） |
| S10 | 云端 WAR/发布 | 云端 WAR、安全审查、发布/回滚、文档/用户测试 | 发布检查表；矩阵报告；回放 0 写 | 云端（可选/后置） |

**MVP 建议范围：S0–S5。** 如果截止日期紧，S0–S3 是最低可演示（0 行 + 纯前端 + 回放）；S4–S5 是“能给自己/别人用”的最低门槛。

## 4. 单人检查点停止与自检协议

到达 S0–S10 任一检查点，**停止继续修改**，执行：

1. 跑验收命令/测试/demo；记录失败和未采集。
2. 写进度包：
   ```text
   CHECKPOINT: S2
   STATUS: done | partial | blocked
   EVIDENCE: 命令/测试/demo/截图/fixture
   CHANGED: 文件/事件字段/API/契约
   RISK: 未采集/性能/兼容/隐私
   NEXT: S3
   ```
3. 用只读 review 会话/子代理自查：契约是否破坏、是否有 secret、是否有静默缺口、回放是否只读、性能是否超预算。
4. 更新本文件/README/契约版本；提交并打 tag。
5. 只有自检通过，才开始下一个检查点。没有队友会签，但**规则本身是硬门**：未通过不跨检查点。
6. 被阻塞时：切到测试/fixture/文档/性能基线；在进度包里写清阻塞，不静默等待。

## 5. 任务安排（按检查点，不按角色/人）

| 检查点 | 采集/Agent | 平台/Collector | 前端/工作台 | 单人验收 |
|---|---|---|---|---|
| S0 | agent 模块骨架 | 仓库/schema/collector mock | AppShell/fixture | 可构建；契约草案 |
| S1 | 最小插桩/一条事件 | ingest/关联 mock | fixture 板/点击事件 | walking skeleton |
| S2 | Boot attach、方法/SQL/行数 | 关联/存储/API | 请求切换/事实图 | 0 行端到端 |
| S3 | 异常/状态字段 | 回放 API | SDK/纯前端/时间轴 | 纯前端 + 回放 |
| S4 | 握手/诊断 | IDEA/JAR launcher/代理 | 详情/×N/缺口 | 本地接入 |
| S5 | L1/字段/脱敏 | sourcemap/存储 | Vite/Vue 浅层插件 | 100→0 参数/字段 |
| S6 | L2/异步/字段写入 | 异步关联/预算 | 逐次调用/行级详情 | 行级 100→0 |
| S7 | Tomcat 或 React 适配 | 对应 runner/CI | 对应前端/组件映射 | 第二栈可用 |
| S8 | 另一栈 | 矩阵/CI | 另一前端/矩阵 UI | 本地矩阵 |
| S9 | 云端镜像/握手 | 沙箱/DB/预览/保留 | 上传/诊断 UI | 云端 Boot |
| S10 | 兼容/性能 | 云端 WAR/安全 | 发布/用户测试 | 发布检查表 |

## 6. 单人任务顺序建议

1. **先 S0–S3**：建立最小事实闭环；不要先做漂亮 UI/完整 agent。
2. **再 S4–S5**：让自己能真实接入项目；这一步最容易暴露路径/Tomcat/代理/CSP 问题。
3. **再 S6**：行级变量/异步；这是最容易拖慢的层，放在闭环之后。
4. **S7–S8**：二栈/三栈扩展；一次只加一条，避免单人同时踩两套框架。
5. **S9–S10**：云端；只有本地闭环稳定且安全隔离有把握再开。云端不是首发必需。

## 7. 单人 Qoder 上下文与文件规则

- 每个检查点只读：`README.md` + 本文件 + 主计划对应章节 + 当前契约/fixture；不要每次把 130KB 主计划全塞进上下文。
- 一个检查点一个 owner 会话；审查用独立 review 子代理；不要同时开多个会写代码的会话。
- 生成代码不手改；schema/API 变更同时更新类型和契约测试。
- 不把真实 secret/客户数据放进 prompt/fixture；默认脱敏。
- GitHub/国内无镜像资源：给用户官方链接、版本、存放位置/校验；不自动下载、不换第三方镜像。
- 提交前跑测试；每个检查点至少一个可回滚 commit/tag。

## 8. 单人范围裁剪（按截止日期）

- **≤ 8–10 周：** 只做 S0–S3（本地 Boot+Vue，0 行/纯前端/回放）；不承诺 React/Tomcat/云端/L2。
- **10–20 周：** 做到 S0–S5（本地 MVP + L1/sourcemap）；S6 视时间；云端不做或只做受邀演示。
- **20–36 周：** S0–S7/S8；本地三栈矩阵；云端只在 S9 之后按安全门禁。
- **36 周以上：** 再考虑 S9/S10 云端与 WAR/完整矩阵；单人完整产品仍应分版本发布，不要一次性承诺。

> 这些是工作量区间，不是同步时钟；是否继续只看当前检查点是否通过。

## 9. 单人开发的主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 范围过大 | 每个都浅、长期没有可演示闭环 | MVP S0–S5；先 0 行/纯前端；扩展按 S7–S10 分批 |
| 上下文过载 | Qoder 忘记契约/改错模块 | 一个检查点一个会话；只读指定文件；契约先行 |
| 单人无交叉 review | 误判/静默缺口 | 每次检查点用 review 子代理；测试/fixture/证据 |
| agent 字节码踩坑 | 应用起不来/性能差 | fail-open；L0 先行；L2 后置；测试矩阵 |
| 云端安全 | 不可信代码/数据泄露 | 强隔离未达标不开放上传；本地优先 |
| 时间/比赛压力 | 赶工造假 | 明确支持矩阵；未完成标“仅本地/暂不支持” |

## 10. 开工前检查表

- [ ] 确认当前目录是否迁到纯 ASCII 路径（或所有脚本加引号、测试中文/空格）。
- [ ] `git init` + `.gitignore`；一个 `main`/短分支策略；不需要 A/B/C worktree。
- [ ] 用 Qoder 打开单人 workspace；确认只有一个 owner 会话。
- [ ] 读 `README.md`、本文件、主计划相关章节；确认 MVP 范围。
- [ ] 从 S0 开始；完成 S0 后停止、自检、提交，再进 S1。
- [ ] 不在未通过 Sx 的情况下开始 Sx+1；不因“今天/本周”跳过检查点。
